## 瀏覽器中的 btoa 為什麼出來的還是字串？

在 [Why were Javascript atob() and btoa() named like that?](https://stackoverflow.com/questions/33854103/why-were-javascript-atob-and-btoa-named-like-that)  這則討論我們可以知道，btoa 的 b 跟 a 分別代表 **binary(b)** 及 **ASCII(a)** ，那依照這個邏輯，btoa 出來的結果應該要是 ASCII 編碼的字串才對。

```js
// A 的 ASCII 編碼是 65
const encodeText = new TextEncoder().encode("A");
console.log(encodeText); // Uint8Array(1) [65]


// 將字串 A btoa 的結果
btoa("A") // "QQ==" 
```

但實際上結果卻是 `"QQ=="`，那這個 ASCII 在哪呢？

從 [MDN](https://developer.mozilla.org/en-US/docs/Glossary/Base64) 我們可以知道

>Base64 is a group of similar binary-to-text encoding schemes that represent binary data in an ASCII string format by transforming it into a radix-64 representation. The term Base64 originates from a specific MIME content transfer encoding.

也就是說 Base64 是將二進位資料轉換成使用 **64 個**字元集的 ASCII 編碼字串，聽起來有點不知所云，來看一下實際例子：

以字串 A 為例，在 [ASCII](https://zh.wikipedia.org/zh-tw/ASCII) 的編碼會是 `65` (十進位)，轉成二進位會是 `01000001`，到這邊就是所謂的 binary 轉成 ASCII 了。

接著我們要將這個二進位轉成 Base64 編碼，也就是 6 bits 為一組，因為這樣就會是 2^6 = 64 個字元，也就是 Base64 的來源。

:::info
64 個字元指的是 A-Z、a-z、0-9、+、/ 總共會是 26 + 26 + 10 + 1 + 1 = 64 個字元。
:::

對應到 Base64 的[索引表](https://zh.wikipedia.org/zh-tw/Base64) 就會是 `QQ==`，那這個 `=` 是指如果原始的字元數量不足 3 的倍數時，就會在最後補上 `=`，以確保 Base64 編碼的長度是 4 的倍數。所以最多只會有兩個 `=`。


## 為什麼一定要以 24 bits 為一組？

前面說到 Base64 會先把 Binary 轉成 8 bits 的 ASCII code，然後以 3 個 ASCII code 為一組，這樣就會是 24 bits，然後再將這 24 bits 分成 4 組，每組 6 bits，這樣就可以對應到 Base64 的 64 個字元。
而這個 24 其實就 6 跟 8 的**最小公倍數**，之所以要以公倍數的方式讓他可以對齊，是因為這樣在轉換的過程才能準確的進行轉換，而 `=` 則可以判斷哪些 bits 是補上的，這樣在解碼的時候就可以知道要怎麼處理。

:::info 如果不是 24 bits 一組會有什麼問題？（已解決）
我研究到這裡時，想說為什麼一定要 24 bits？我不能就讓他 6 個一組剩下的就補零就好啦，然後要還原時，只要 8 bits 為一組，剩餘的一定是填充把它去掉，這樣 'A' 就會變成 'QQ'，不就更短了嗎？

## 那 `=` 到底是不是必要的？

後來去翻了 [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648.html)，才發現這個問題的答案其實很簡單：**`=` 的填充本來就不是必要的**，所以上面那個想法沒有錯。

規格的 [3.2 節 Padding of Encoded Data](https://www.rfc-editor.org/rfc/rfc4648.html#section-3.2) 是這樣寫的：

> In some circumstances, the use of padding ("=") in base-encoded data is not required or used. In the general case, when assumptions about the size of transported data cannot be made, padding is required to yield correct decoded data.

簡單來說就是，只有在「無法預先知道資料有多長」的情況下才需要 `=`。

所以 `=` 的工作其實不是拿來算長度的（就像上面說的，除以 8 就知道了），而是拿來**標記邊界**。Base64 是 email（MIME）時代的產物，當時的情境是一條資料流一直流過來，收的人不知道總長度，只能邊收邊解，這時候就需要一個記號告訴他「這一包到這邊結束」。

不過在現代大部分的情境下，我們一開始就拿到完整的字串了，這個記號自然就沒什麼用。而且有趣的是，`atob` 本身也不在乎有沒有 `=`：

```js
btoa("A")    // "QQ=="  ← 一定會補
atob("QQ")   // "A"     ← 沒補也解得出來
```

也就是說，解碼的時候從頭到尾都沒有非要 `=` 不可。

### 那有哪些是沒補的？

實際上已經有不少地方是不補 `=` 的：

**1. JWT**

JWT 的 [RFC 7515](https://datatracker.ietf.org/doc/html/rfc7515#section-2) 直接規定要把結尾的 `=` 全部拿掉：

```js
// btoa 的結果
btoa('{"sub":"123","name":"Jim"}')
// → eyJzdWIiOiIxMjMiLCJuYW1lIjoiSmltIn0=

// JWT 實際長的樣子
// → eyJzdWIiOiIxMjMiLCJuYW1lIjoiSmltIn0
```

它敢拿掉的原因也很好理解，JWT 本身是 `header.payload.signature` 三段用 `.` 隔開，那個 `.` 就已經是邊界記號了，再補一個 `=` 反而多餘。

**2. base64url**

JWT 用的其實是 base64url，除了不補 `=` 之外，還會把 `+` 換成 `-`、`/` 換成 `_`，這樣才能安全地放進網址跟 header 裡。

**3. Uint8Array.prototype.toBase64**

ES2026 的新 API 直接開了一個選項讓你自己決定：

```js
new Uint8Array([65]).toBase64()                      // "QQ=="
new Uint8Array([65]).toBase64({ omitPadding: true }) // "QQ"
```

至於 `btoa` 為什麼不能選，是因為它 1997 年就存在了，行為被規格寫死，改了會弄壞一大堆舊網站，所以只能一路補下去啦。


## Base64 原始碼

我在研究上面那個待解決問題時，想說來找一下 chromium 怎麼實作的，但都找不到，只有在 [Chromium Issues](https://issues.chromium.org/issues/40339718) 找到 2013 有修過 atob，但是當初實作的路徑現在已經找不到了，後來我只有找到 [WebKit](https://github.com/WebKit/WebKit/blob/152b90c32f5dec65fa0a6d30bfb7e9f934fd7b5d/Source/WebCore/page/WindowOrWorkerGlobalScope.cpp#L41) 的實作，另外也有人實作 [base64-js](https://github.com/beatgammit/base64-js/blob/master/index.js)，有興趣的人可以看看～

## Unit8Array toBase64/ fromBase64

在看實作 Base64 的過程，想說是不是應該要有個 Unit8Array 直接轉 Base64 的方法，因為 btoa 只能傳字串，所以如果是 Unit8Array 的話還需要先用 `TextDecoder` 轉成字串，後來就找到這個熱騰騰還在 Stage3 的 [proposal](https://github.com/tc39/proposal-arraybuffer-base64)，會找到主要是看到 [Chromium Issues](https://issues.chromium.org/issues/42204568) 有在討論要實作這個他，所以應該過不久就可以使用了！

### 2026/09/08 更新：已經可以用了

這個 proposal 在 2025 年就進到 [Stage 4](https://github.com/tc39/proposal-arraybuffer-base64/issues/51)，正式收進 **ES2026**，Chrome、Firefox、Safari 跟 Node 22+ 現在都能直接用了，不用再等囉～

```js
const bytes = new Uint8Array([72, 101, 108, 108, 111]);

bytes.toBase64();                      // "SGVsbG8="
bytes.toBase64({ omitPadding: true }); // "SGVsbG8"

Uint8Array.fromBase64("SGVsbG8=");     // Uint8Array(5) [72, 101, 108, 108, 111]
```

除了 `toBase64` / `fromBase64` 之外，它還一併加了 `toHex` / `fromHex`，而且上面提到的 `omitPadding` 選項也是這時候一起進來的。
